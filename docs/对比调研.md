## 0. 一句话结论

**大方向（本地、批量、离线、调质量/尺寸压图）早就有人做了，而且做得比我们成熟得多。**

但"**只给字节上限，程序自己在「分辨率 × 质量」二维空间里搜，并对扫描件这类文字材料优先保分辨率**"这一整套组合，我在开源工具里没找到等价物。

单个能力几乎都能找到前人：按目标体积压（jpegoptim、ImageMagick）、质量和感知指标寻优（jpeg-recompress）、批量 GUI（Caesium、ImageOptim）、重采样（ImageMagick、sharp）。**没人把它组合成"上传材料专用"的一件事。**

| 类别 | 代表 | 一句话定位 |

| A. 命令行压缩器 | jpegoptim、mozjpeg/cjpeg、jpeg-archive、pngquant、oxipng | 单个格式的极致优化，脚本友好，不做"整体方案" |

**读表要点：**

* 第 1 行就分出了两类工具：**"按体积"** 和 **"按质量"**。绝大多数工具是后者。
* 真正做到"按体积"的两个（jpegoptim `--size`、ImageMagick `jpeg:extent`），
  **都只调质量、不调分辨率**，所以它们解决不了"7.4MB 手机拍的证书 → 200KB"这种场景：
  尺寸不降，质量压到底也到不了 200KB，甚至会把字压烂。
* jpegoptim 的 man page 自己在 BUGS 里写着：*"When using --size option, resulting file is not always exactly the requested size.
  Workaround is to re-run jpegoptim on the same file again"* [1] —— 即它**不保证达标**。
* jpeg-recompress 是"感知质量寻优"（SSIM/MS-SSIM 目标），不是体积目标 [2]。
* Squoosh 至今没有"按目标体积设质量"的功能，GitHub 上还有对应的 feature request [3]。

## 3. 我们真正独到的地方

### 3.1 把"体积"当成一等约束，而不是结果

别人的调用模型是 `输入 → 质量参数 → 输出（体积未知）`；
我们是 `输入 + 体积上限 → 输出（体积确定 ≤ 上限）`。

这不是包装差异：它决定了**失败模式**。前者在 200KB 卡死的报名系统上会反复试错；
后者一次到位，因为搜索是在真实编码字节数上做的（`engine.encode()` 每次真编码、量长度）。

### 3.2 二维搜索 + 内容类型决定优先级

这是我认为最核心的一条。**同一个预算下，"先降分辨率"和"先降质量"是两种截然不同的图像损伤**：

* 文字材料：信息在分辨率里，质量降到 40 仍能辨认（实测成绩单 934×1320 @ q40 清晰可读）
* 照片：信息在灰阶里，质量降到 40 会出现块状色带

所以默认走 `resolution` 模式（保分辨率），照片类显式切 `quality` 模式（保保底质量 75）。
据我检索，**没有任何一个开源压缩工具把"内容类型"作为搜索方向的输入**——
它们要么只有质量一个旋钮，要么把分辨率当独立参数交给用户。

### 3.3 达标是"证明"出来的，不是"希望"出来的

三层保证，别人大多没有：

1. 搜索阶段用真实编码字节数判断（估算误差 20%~30%，不可接受）
2. 落盘用原子写（`.part` → `fsync` → `os.replace`），断电不留半截文件
3. 写完**重新打开解码**，比对字节数与尺寸（`_verify_output`）

这条和 jpegoptim 的 BUGS 条目正好形成对照 [1]。

### 3.4 针对"网申上传"这个场景的细节，别处没有

* **默认留 5KB 余量**：`200KB` 在系统中可能被算成 204800 或 200000 字节，两种口径都过
* **总量预算**：`--total 2mb` 用"装水"算法分配，小图只拿自己那份，余量回流给大图
* **已达标按字节复制**：不为了省 5KB 再压一次
* **同名文件按目录前缀区分**：`A_证书.jpg` / `B_证书.jpg`，而不是 `证书(1).jpg`
* **默认清元数据**：求职材料里的 GPS、设备、序列号没有理由跟着外传

这些单独看都不"高级"，但都是真实上传过程中被咬过才会想到的东西。

### 3.5 工程形态：一个仓库同时是 CLI + GUI + 测试 + CI

同类工具通常是"一个 CLI"或"一个 GUI"，二选一；有 CI 和 81% 覆盖率的更少。
对我们这种"给同学用"的场景，双击 `run-gui.bat` 就能跑、同时又能写进脚本，是有意义的。

## 4. 别人比我们强的地方（诚实清单）

不写这一段，这份文档就没有价值。

| 维度 | 谁更强 | 说明 |
| --- | --- | --- |
| **极限压缩率 / 画质** | mozjpeg、jpeg-recompress、AVIF/JPEG XL | 我们用 Pillow 内置的 libjpeg-turbo，参数上只到 `optimize + progressive + 4:2:0`；mozjpeg 的 trellis 量化、jpeg-recompress 的 SSIM 感知调优，同体积下画质更好 |
| **无损优化** | jpegoptim、oxipng、ECT | 我们只重编码，不做"无损重排 Huffman/元数据"这一类；对本来就好的 JPEG，我们能省的更多是"重压"，他们会省得"无损" |
| **速度** | jpegoptim（C）、caesiumclt（Rust） | 我们是 Python，单张 0.3~1 秒；批量上百张时才看得出差距 |
| **格式广度** | ImageMagick、Squoosh、Caesium | 我们输出只有 JPEG，PNG/WebP/AVIF/HEIC 都不支持 |
| **成熟度与生态** | 上面全部 | 它们被发行版打包、有十年以上的 issue 历史；我们是 3000 行、单人、两个月 |
| **感知质量评估** | jpeg-recompress | 它有 SSIM/MS-SSIM/butteraugli 一类指标做目标，我们只用固定质量档位 + 分辨率网格 |
| **云服务算法** | TinyPNG 等 | 闭源、效果更好，但要求上传（对隐私敏感的材料不合适） |

**这也是为什么我们的定位不能是"最好的图片压缩器"**——在那个赛道上我们排不上号。
我们能站住的位置是：**"把材料塞进上传限制"这件事的开箱即用方案。**

## 5. 技术亮点（可写进简历/面试的部分）

### 算法层

1. **不做体积估算，逐点实测**：JPEG 体积受内容复杂度影响，公式误差 20%~30%；
   我们对每个候选 `(长边, 质量)` 真编码一次、用返回长度判断（`engine._Fitter.encoded`）。
2. **剪枝 + 二分把搜索压到 17~18 次编码**：
   先用最低质量淘汰过大的尺寸（1 次编码/尺寸），再对质量二分（≈5 次），
   并对 `(长边, 质量)` 做缓存。20 张图（含 7.4MB 大图）总耗时 7.2 秒。
3. **两种搜索方向**：`resolution`（分辨率优先，文档类）/ `quality`（质量优先，照片类），
   各自把不重要的那个维度只做保底。
4. **总预算装水分配**：不是平分，而是"小图只拿自己需要的、余量回流给大图"。

### 工程层

5. **达标可证明**：编码实测 + 原子写 + 落盘后重新解码校验。
6. **并行确定性**：目标文件名在主进程统一分配，`-j1` 与 `-j4` 产物逐字节一致
   （这个 bug 只有并行才暴露，修完补了"子进程真跑 `-j2` 再逐字节比对"的测试）。
7. **路径归一化**：`_canonical()` 处理 macOS `/var → /private/var` 软链与 Windows 8.3 短名，
   否则会把源文件当"新文件"覆盖掉（这两个坑都是 CI 在 macOS/Windows 上红出来的）。
8. **失败隔离**：单张坏图返回 `FileResult(action="failed")`，整批继续，CLI 退出码 1。
9. **GUI 线程模型**：worker 线程只往 `queue.Queue` 塞消息，主线程 `after(100)` 轮询刷新，
   避开 Tkinter 的跨线程禁忌。

## 6. 建议的对外表述（能说什么、别说什么）

**可以这么说：**

> "面向网申/报名材料的批量图片压缩工具：给出字节上限（如 200KB），自动搜索分辨率与质量，
> 扫描件优先保分辨率、照片优先保画质；落盘后校验，保证不超标；CLI 与 GUI 同一套内核，纯本地离线。"

**别说成：**

* ❌ "最强的图片压缩器"（画质/压缩率上比不过 mozjpeg 系）
* ❌ "业界首创按体积压缩"（jpegoptim 的 `--size`、ImageMagick 的 `jpeg:extent` 早就有）
* ❌ "支持所有格式"（只有 JPEG 输出）
* ❌ "比 TinyPNG 压得更小"（没测过，且大概率不是）

**唯一站得住的"首创"级表述：**

> "把'字节上限'作为唯一输入，并让搜索方向随内容类型切换（文字保分辨率 / 照片保画质）——
> 这个组合在现有开源工具里我没找到等价实现。"

这句话有边界、可被验证，也不吹。
