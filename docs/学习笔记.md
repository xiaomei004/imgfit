## 1. 起点：一个具体到不能再具体的问题

2026 年 10 月，投某国企的网申系统，材料上传限 **单张 200KB**。手上是什么：

| 材料 | 原大小 |
| --- | --- |
| 校级 ACM 算法竞赛证书（手机拍的） | 7.4 MB |
| 省部级蓝桥杯证书（扫描件，A4 300dpi） | 1.3 MB |
| 成绩单（扫描件，带密集水印） | 981 KB |
| 就业推荐表 | 317 KB |

用现成工具会掉进两个坑：

* **压不达标**：在线压缩网站经常"压到 400KB 就不肯再小"，而系统硬卡 200。
* **达标但糊字**：一键压到 50% 质量，成绩单里的分数`79`、`*65`（补考标记）挤成一团黑块。

于是有了这个工具的第一条设计原则：**不要把"质量参数"交给用户，用户给字节上限，程序自己找参数。**

第二个月再回头看，这句话其实是整个项目的种子：它把问题从"调个质量滑块"变成了一个**约束最优化问题**：

> 在 `输出字节数 ≤ B` 的约束下，让"视觉可用性"最大。

## 2. 需求是怎么变成参数的

`FitConfig`（`src/imgfit/engine.py`）里的每一个字段都对应一个真实世界的约束，没有一个是凭空调出来的：

| 参数 | 默认 | 它解决什么 | 为什么会存在 |
| --- | --- | --- | --- |
| `budget` | 200 × 1024 | 硬上限 | 系统卡的就是这个数 |
| `mode` | `resolution` | 先保分辨率还是先保质量 | 文字材料和照片的"信息分布"不同 |
| `min_quality` | 按模式：文档 10 / 照片 40 | 质量下限 | 低于它不如继续缩尺寸。**0.1.x 里固定写死 40，是拍脑袋的，见 6 节坑 11** |
| `max_quality` | 92 | 质量上限 | 92 以上收益极小、体积涨得快 |
| `target_quality` | 75 | 质量优先模式的保底 | 照片低于 75 就肉眼可见了 |
| `max_dim` | 2200 | 长边上限 | 再大对上传毫无意义，纯浪费预算 |
| `floor_dim` | 800 | 长边下限 | 分辨率优先模式不允许为了达标无限缩小 |
| `hard_min_dim` | 320 | 绝对下限 | 极端预算下最后一根救命稻草 |
| `dim_step` | 50 | 尺寸搜索步长 | 50px 一档，再细收益很小、耗时翻倍 |
| `subsampling` | 2（4:2:0） | 色度抽样 | 体积直降约 20%，文字笔画靠亮度通道保住 |
| `copy_if_fits` | True | 已达标就不重压 | JPEG 每次转码都是又一次有损 |
| `keep_metadata` | False | 是否保留 EXIF/ICC | 手机照片带 GPS、设备、序列号 |
| `background` | 白 | 透明图转 JPEG 的底色 | 不填白，透明区域会变成黑色 |

**这里有个值得体会的点**：写代码时最容易犯的错是直接暴露实现细节（`--quality 65 --scale 0.7`），而把领域约束翻译成参数（`--target 200kb`）才是产品。参数表的设计就是"把复杂度留给自己"的过程。

## 3. 架构：四个模块各管什么

```
                    ┌─────────────────────────────┐
   命令行 / 图形界面  │  cli.py          gui.py     │  ← 只管交互：解析参数、显示进度
                    └──────────────┬──────────────┘
                                   │  共用同一套调用
                    ┌──────────────▼──────────────┐
                    │  pipeline.py                 │  ← 只管编排：收集文件、分预算、
                    │  collect → 分配 → 并行 → 报告 │     分配文件名、并发、导出报表
                    └──────────────┬──────────────┘
                                   │  每张图一次调用
                    ┌──────────────▼──────────────┐
                    │  engine.py                   │  ← 只管一张图：解码、搜索、
                    │  prepare → fit → 写盘 → 自检  │     编码、落盘、验证
                    └─────────────────────────────┘
                                   │
                    ┌──────────────▼──────────────┐
                    │  size.py                     │  ← 只管字符串："200kb" → 204800
                    └─────────────────────────────┘
```

**分层的目的不是"好看"，而是让 CLI 和 GUI 不可能行为不一致。** 两者都只做一件事：
把用户输入翻译成 `BatchOptions`，然后调用 `run_batch`。GUI 那 400 行里没有一行压缩逻辑。

一次批量调用的时序：

```
run_batch(inputs, options)
  ├─ collect_inputs()        展开文件夹、去重、跳过输出目录
  ├─ _budgets_for()          每张图分到多少字节（单张预算 or 总预算装水分配）
  ├─ plan_targets()          一次性决定所有输出文件名  ← 并行确定性的关键
  ├─ for each file:
  │     compress_file()
  │       ├─ prepare()       按 EXIF 转正、透明拍平、转 RGB
  │       ├─ fit()           （分辨率 × 质量）网格搜索
  │       ├─ _write_atomic() 先写 .part，fsync，再 os.replace
  │       └─ _verify_output() 重新解码，比对字节数与尺寸
  └─ report.results          汇总；失败的文件不抛异常，只记录
```

## 4. 核心算法

### 4.1 为什么不信公式

最容易想到的做法：`体积 ≈ 宽 × 高 × 每像素比特 / 质量系数`。这个估算误差能到 20%~30%，因为 JPEG 是熵编码，实际大小取决于图像的局部高频成分。

同一张 1358×1920 的成绩单，实测（单位 KB）：

| 长边 | q90 | q80 | q70 | q60 |
| --- | --- | --- | --- | --- |
| 2000 | 864 | 685 | 587 | 506 |
| 1600 | 716 | 519 | 420 | 358 |
| 1400 | 569 | 410 | 331 | 280 |
| 1200 | 431 | 309 | 250 | 211 |
| 1000 | 304 | 217 | 173 | 144 |

看出两件事：体积随尺寸下降**远非线性**（2000→1000 长边，q80 只从 685 降到 217，不是 1/4）；而且同一尺寸下质量档位之间的落差也不均匀。

所以 `engine.encode()` 的做法很朴素：**真编码一次，用返回的字节串长度判断**。

```python
def encode(im, quality, cfg, exif=None, icc=None) -> bytes:
    buf = io.BytesIO()
    im.save(buf, format="JPEG", quality=int(quality), optimize=True,
            progressive=True, subsampling=cfg.subsampling)
    return buf.getvalue()
```

代价是 CPU 时间（每张图编码十几次），换来的是"**绝不交付超标文件**"。对我们这种一次几十张图的场景，这个 trade-off 完全划算：20 张图总共 7 秒。

### 4.2 两个自由度 → 两种模式

预算固定时只有两个旋钮：**分辨率**和**质量**。它们对"能不能看清"的贡献完全不同：

* 文字材料（成绩单、证书）：信息在分辨率里。分辨率砍半 = 笔画被抽掉，质量再高也救不回来。
* 照片：信息分散在灰阶里。质量过低会出现大面积色块，而分辨率不足只是"看起来小一号"。

同一张 981KB 成绩单、同样 195KB 预算下的实测对比（我把两块文字区放大 2 倍并排看过）：

| 方案 | 分辨率 | 质量 | 结论 |
| --- | --- | --- | --- |
| 分辨率优先 | 934×1320 | q40 | 课程名、分数、印章文字都能认 |
| 中间点 | 849×1200 | q57 | 略软 |
| 质量优先 | 707×1000 | q74 | 没有块状伪影，但字太小 |

**这就是默认值的由来**，也是"为什么第一版被我推翻"的原因（见第 6 节坑 1）。

### 4.3 搜索空间与剪枝

长边候选：从 `min(原图长边, 2200)` 递减到 `floor_dim`（800），步长 50，大约 28 个；质量候选：92 递减到 40，步长 2，共 27 个。

暴力遍历是 28 × 27 ≈ 756 次编码，太慢。实际用的是"**先判断这个尺寸有没有希望**"：

```python
def search_resolution(self, sides):           # 分辨率优先
    levels = _levels(92, 40, 2)               # [92, 90, ..., 40]
    for long_side in sides:                   # 从大到小
        if not self.fits(long_side, 40):      # ① 连 q40 都超标 → 只花 1 次编码就淘汰
            continue
        index = self._best_quality_index(long_side, levels)   # ② 二分出最高可用质量
        if index is not None:
            return self._result(long_side, levels[index])
```

关键两点：

* **第 ① 步**：绝大多数"过大"的尺寸只需 1 次编码就被淘汰，不进内层循环。
* **第 ② 步**：`fits(质量)` 是单调的（质量越低体积越小），所以能二分，log₂27 ≈ 5 次。

实测每张图的编码次数是 **17~18 次**（用 `FitResult.encodes` 打出来的），比线性扫描质量那次实现快了约 30%（20 个文件 10.4s → 7.2s），而**产物逐字节一模一样**。

质量优先模式方向相反：先定质量（75），再二分查找"能塞得下的最大长边"：

```python
def _largest_fitting_side(self, sides_asc, quality):
    low, high, best = 0, len(sides_asc) - 1, None
    while low <= high:
        mid = (low + high) // 2
        if self.fits(sides_asc[mid], quality):
            best = sides_asc[mid]
            low = mid + 1          # 还能更大
        else:
            high = mid - 1
    return best
```

### 4.4 缓存：同一组参数只编码一次

`_Fitter` 里两个字典：

```python
self._resized: Dict[int, Image.Image] = {}          # 长边 → 缩放后的图
self._encoded: Dict[Tuple[int, int], bytes] = {}    # (长边, 质量) → 字节串
```

搜索过程中同一个 `(长边, 质量)` 会被多次问到（剪枝判断、二分、最后取结果），缓存让这些询问变成查表。`FitResult.encodes` 记录真实编码次数，方便以后优化时有据可依。

### 4.5 兜底：宁可报错，也不交超标文件

所有网格都失败时还会向下探到 `hard_min_dim`（320px）；再失败就抛 `FitError`，并带上"最小也需要多少字节"：

```python
raise FitError(
    "预算 {budget} 字节过小：即使缩到 {dim}px、质量 {q} 也还需 {need} 字节".format(...)
)
```

**静默交付一个 220KB 的文件让用户上传失败**，比明确报错糟糕得多。

## 5. 十二个"看起来多余"的细节

这些都来自真实踩坑或明确的工程判断，删掉任何一个都会留下隐患。

### 5.1 已经是小图就不重压（`copy_if_fits`）

英语四级 183KB，已在 200KB 内。重新编码只会让它更糊，唯一收益是省 5KB——不值得。所以直接按字节复制，`action="copied"`。

### 5.2 默认留 5KB 余量

`200KB` 有两种口径：`200 × 1024 = 204800` 和 `200 × 1000 = 200000`。不同系统的校验代码各不相同。CLI 默认算 `204800 - 5120 = 199680`，最"胖"的产物是 199609 字节——两种口径都能过。

小目标按比例缩：`max(1024, min(5120, budget // 20))`，20KB 的目标留 1KB。

### 5.3 原子写：先写 `.part`，再 `os.replace`

```python
tmp = path.with_name(path.name + ".part")
with open(tmp, "wb") as handle:
    handle.write(data)
    handle.flush()
    os.fsync(handle.fileno())
os.replace(tmp, path)
```

中途断电 / Ctrl+C 只会留下一个 `.part`，绝不会出现"半个 JPEG"被当成成品上传。

### 5.4 落盘自检：写完再验证一遍

```python
def _verify_output(path, budget, expected_size):
    if path.stat().st_size > budget:
        raise FitError(...)
    with Image.open(path) as check:
        check.load()                      # 真正解码，确认没截断
        if tuple(check.size) != tuple(expected_size):
            raise FitError(...)
```

理论上前面已经精确量过字节数，但磁盘满、权限、杀软占用这些情况只有写完才知道。

### 5.5 目标文件名在主进程统一分配（并行确定性的关键）

这个 bug 是 0.1.1 修的，值得单独讲，因为它是"**顺序执行时完全看不出来**"的典型。

原来的做法：每个 worker 自己去输出目录里找空名字（`unique_target()`）。单进程时按输入顺序执行，结果确定。但 `-j 4` 时两个 worker 可能同时看到"`证书.jpg` 这个名字没人用"，于是谁先写完谁占住它——**两个不同内容的文件互换名字**。

实测就是这个名字互换：产物 `表彰奖励证明材料.jpg` 在 `-j1` 下是 199300 字节，在 `-j4` 下变成 194254 字节（两张图的内容完全一样，只是名字对调了）。

修法是把"分配名字"从并发区里拿出来：

```python
targets = plan_targets(inputs, sizes, budgets, options)   # 主进程，顺序，一次算完
payloads = [(src, out_dir, cfg, overwrite, str(target)) for ...]   # 分给 worker
```

顺带解决了另一个隐患：两个 worker 抢同一个名字时，可能互相覆盖。

### 5.6 同名文件用上级目录前缀区分

`A/证书.jpg` 和 `B/证书.jpg` 同时处理时，原来会产出 `证书.jpg` + `证书(1).jpg`——用户根本分不清哪个是哪个。现在产出 `A_证书.jpg`、`B_证书.jpg`。

### 5.7 三层保护：永远不覆盖源文件

1. `_reserve()` 里维护 `batch_sources`（本批次所有源文件），命中就换名字；
2. `unique_target()` 在单文件模式下也会比较目标与源文件是否同一个路径；
3. `run_batch` 的 `collect_inputs` 默认跳过输出目录。

第一层是 0.1.1 加的：以前只保护"自己"，`-o .` 这种"输出目录就是输入目录"的情况下，A 的产物有可能覆盖 B 的源文件。

### 5.8 总预算的"装水"分配

`--total 2mb` 时不能简单平分：3 张图本来只有 80KB，给它们各自 220KB 的额度是浪费。算法是模拟装水：

1. 平分剩余额度；
2. 本身不超过均摊额度的文件，只拿自己那份（它会被原样复制），退出队列；
3. 省下的额度回流，继续平分给大文件；
4. 每个文件保底 4KB。

实测 3 张噪声图 + 2MB 总额度，产物总量严格 ≤ 2MB。

### 5.9 失败隔离：`compress_file` 不抛异常

单张图损坏（截断的 JPEG、0 字节文件、不支持的编码）不应该让整批 20 张全白干。所以 `compress_file` 的返回类型是 `FileResult`，失败时 `action="failed"`、原因写进 `detail`：

```python
except Exception as exc:
    return FileResult(source=source, target=None, action=ACTION_FAILED,
                      detail=f"{type(exc).__name__}: {exc}", ...)
```

CLI 最后按失败数量返回退出码 1，方便脚本判断。

### 5.10 GUI 用 `queue` + `after` 轮询，不跨线程碰控件

Tkinter 的规则：**控件只能在主线程操作**。所以后台线程只往 `queue.Queue` 塞消息，主线程用 `root.after(100, self._drain)` 每 100ms 取一次：

```python
def _worker(self, files, options):
    report = run_batch(files, options,
                       progress=lambda done, total, r: self.queue.put(("progress", (done, total, r))),
                       should_cancel=self.cancel_event.is_set)
    self.queue.put(("done", report))
```

取消用 `threading.Event`，worker 通过 `should_cancel` 回调检查，已完成的产物保留。

### 5.11 EXIF 转正 + 透明拍白底

两行代码解决两个能毁掉整张图的问题：

```python
im = ImageOps.exif_transpose(raw)     # 手机竖拍的照片，像素其实是横的
...
canvas = Image.new("RGB", rgba.size, background)
canvas.paste(rgba, mask=rgba.getchannel("A"))   # 不拍平，透明区在 JPEG 里会变黑
```

### 5.12 默认清除 EXIF/ICC

手机拍的材料带 GPS 坐标、设备型号、拍摄时间，部分机型还写序列号。求职材料外传时这些没有任何理由跟着走。需要保留（例如带版权信息的作品）加 `--keep-metadata`。

## 6. 踩坑实录

按发生顺序，都是真实踩到的。

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 第一版压完，成绩单字糊成一个黑团 | 我按"保质量 q≥72"实现，分辨率被砍到 707×1000 | 改成分辨率优先；实测 q40 + 大尺寸可读性更好 |
| 2 | 终端里中文全是 `锟斤拷` | PowerShell 抓子进程输出时用了另一种代码页 | 脚本里设 `PYTHONUTF8=1`，`.bat` 也设 |
| 3 | `pip install -e .` 报没有 setuptools | Python 3.12 的 venv 默认不带 setuptools，构建隔离要联网下载 | 离线场景改用 `python -m imgfit` / `run-gui.bat`；README 写明 |
| 4 | GitHub 仓库描述变成 `????????` | PowerShell 发 JSON 请求体时用了非 UTF-8 编码 | 用 `[Text.Encoding]::UTF8.GetBytes()` 显式编码 |
| 5 | `.bat` 在 cmd 里执行异常 | LF 行尾 | `.gitattributes` 里 `*.bat text eol=crlf` |
| 6 | "损坏文件"测试居然是绿的 | 那个假文件只有 9 字节，**小于预算**，走了"复制"分支根本没解码 | 把假文件写成 700KB，逼它走编码分支 |
| 7 | 总预算分配时 100 字节的小文件被抬成 1024 | 下限判断写反了：`allocation[i] < minimum` 应该再加 `and sizes[i] > allocation[i]` | 见 `allocate_budgets` 注释 |
| 8 | `-j 4` 与 `-j 1` 产物名字对调 | 并发区里各自找空文件名（见 5.5） | 主进程统一分配 |
| 9 | GUI 按钮状态错乱 | 我用一坨三元表达式写 `_set_running`，自己都读不懂 | 老老实实 if/else |
| 10 | 改 `pyproject.toml` 把中文全写坏了 | PowerShell 的 `Get-Content \| Set-Content` 往返编码不一致 | 用编辑工具改文本文件，别用 shell 管道转码 |
| 11 | 压缩产物的字比"照片应用拉到底"还糊 | 质量下限被全局写死成 40，把"原分辨率 + q14"这个更优解排除在候选之外（0.2.0 修） | 质量下限按内容类型分别给：文档 10、照片 40 |

**这十条里有六条是"顺序执行看不出来 / 小数据看不出来 / 单平台看不出来"**。这也是为什么要有矩阵 CI 和"子进程真跑一遍"的测试。

## 7. CI/CD 笔记

### 7.1 一个 push 之后发生了什么

```
git push origin main
   │
   ├─→ GitHub 收到代码，更新仓库（这一步几乎零成本，不消耗 Actions 分钟）
   │
   └─→ 检查 .github/workflows/*.yml 里有没有 on.push 匹配的分支
          ├─ 没有 workflow 文件 → 什么也不发生（你之前的 9 个仓库就是这样）
          └─ 匹配 → 创建一次 workflow run
                      ├─ 展开 matrix：3 OS × 2 Python = 6 个 job
                      ├─ 每个 job 分配一台全新虚拟机（runner）
                      │     checkout → 装 Python → pip install → ruff → pytest → 冒烟
                      └─ 全部结束 → 销毁 VM、汇总结果、在 commit 上打绿勾/红叉
```

本项目 run #2 的真实时间线（2026-10-21 09:55:03 触发，09:57:00 结束，共 117 秒）：

| job | 时长 | 主要耗时 |
| --- | --- | --- |
| ubuntu · py3.9 | 34 s | setup-python 10s + 依赖 5s + pytest 11s |
| ubuntu · py3.12 | 29 s | |
| windows · py3.12 | 42 s | |
| macos · py3.12 | 30 s | |
| macos · py3.9 | 56 s | setup-python 26s（缓存没命中） |
| windows · py3.9 | 82 s | 排队 30s 后才开始，setup-python 46s |

结论：**大头不是你的测试（11 秒），而是装环境**。这也是为什么 CI 里 `cache: pip` 很关键。

### 7.2 四层概念，别混

| 层 | 是什么 | 本项目的例子 |
| --- | --- | --- |
| **workflow** | 一个 YAML 文件 = 一套流水线 | `.github/workflows/ci.yml` |
| **job** | 一台机器上跑的一组步骤，job 之间默认并行 | `ubuntu-latest · py3.9` |
| **step** | job 里的一个命令或一个 action | `python -m pytest` |
| **runner** | 真正执行 job 的虚拟机 | GitHub 托管的 `ubuntu-latest` |

一个 workflow run = 多个 job = 多台 VM；每台 VM 里顺序执行多个 step。

### 7.3 矩阵：一行 YAML 变成 6 台机器

```yaml
strategy:
  matrix:
    os: [ubuntu-latest, windows-latest, macos-latest]
    python: ["3.9", "3.12"]
```

笛卡尔积 = 6。为什么要这么多？

* **OS**：代码里有路径处理、`os.startfile`、多进程 spawn 语义——只在 Windows 上测等于没测跨平台。
* **Python 版本**：`requires-python = ">=3.9"` 是你对用户的承诺，得证明 3.9 真能跑。

对应的现实问题：macOS 和 Linux 的 runner 没有显示器，`tk.Tk()` 会抛错——所以 GUI 测试写成"拿不到窗口就 skip"，否则那 4 个 job 会红。

### 7.4 计费：什么消耗、什么不消耗

| 动作 | 是否消耗 | 说明 |
| --- | --- | --- |
| `git push` 本身 | ❌ | 只写 git 存储 |
| 触发 workflow 后的 VM 运行 | ✅ | 按分钟计，**向上取整**（42 秒算 1 分钟，82 秒算 2 分钟） |
| 排队等 VM 的时间 | ❌ | 只算真正运行的时间 |
| 公开仓库 | **免费**（标准 runner） | GitHub 对开源项目的资助 |
| 私有仓库 | 从每月额度扣 | Free 账户 2000 分钟/月 |
| 倍率 | Linux 1× / Windows 2× / macOS 10× | 所以 macOS 那两个 job 吃掉 71% 的额度 |

按本项目的数据估算：如果仓库是私有的，一次 push ≈ `(1+1) + (1×2 + 2×2) + (1×10 + 1×10) = 28` 分钟。一个月 2000 分钟 ≈ 70 次 push。现在仓库公开，实际计费是 0——这是我用 `runs/{id}/timing` 接口查出来的（返回 `total_ms: 0`，同时 `run_duration_ms: 117000`）。

### 7.5 覆盖率是怎么进 CI 的（一条不依赖第三方的链路）

```
pytest --cov=imgfit --cov-report=xml
        ↓ 产出 coverage.xml（<coverage line-rate="0.88">）
        ↓ 只从 ubuntu+py3.12 那个 job 上传 artifact
actions/upload-artifact@v4
        ↓
badge job（needs: test，只在 push 到 main 时跑）
        ↓ python3 tools/coverage_badge.py 解析 line-rate → 生成 SVG
        ↓ git clone --branch badges → 替换 coverage.svg → push
        ↓
README 里的徽章指向 raw.githubusercontent.com/.../badges/coverage.svg
```

为什么不用 Codecov/Shields？

* Shields 的 `endpoint` 需要公开一个返回 JSON 的地址，得额外托管；
* Codecov 要给第三方 GitHub App 授权、把覆盖率数据托管出去；
* 而"解析一个 XML、拼一段 SVG"只有 100 行标准库代码。

**这就是"能自己写 100 行就别引入一个依赖"的判断。**

`badges` 分支只放一张 SVG，push 到它不会触发 CI（`on.push.branches` 只监听 main），所以不会自激。

### 7.6 Dependabot 在流水线的位置

```yaml
# .github/dependabot.yml
package-ecosystem: pip → 每月检查 Pillow/pytest 有没有新版本
                     → 有就提 PR
                     → PR 自动触发 ci.yml（因为配了 on.pull_request）
                     → CI 绿了才合
```

它把"依赖升级"这个容易被忘的事变成一条待办 PR。**注意它是"检查 + 提 PR"，不自动合并**——自动合并依赖升级是给自己挖坑。

### 7.7 CI 与 CD：两个概念、两种 CD

* **CI（持续集成）**：代码一变就自动构建 + 测试，保证"库里的代码一直是好的"。
* **CD 有两种**：
  * Continuous **Delivery**（持续交付）：任何通过 CI 的版本**随时可以**发布（打了 tag、产物就绪），但上线那一下要人点。
  * Continuous **Deployment**（持续部署）：通过 CI 就自动上生产，无人值守。

本项目目前是 CI，加上"tag → 构建 wheel → 发 Release"的话就是 Delivery。要变成 Deployment 得有服务端和监控，工具类项目不需要。

企业里"CI 必做、CD 分层"：互联网公司多用 Delivery + 灰度发布，强合规行业（银行、国企、医疗）常在内网自建 Jenkins/GitLab CI，上线要工单和双人复核。**"有 CI 但只跑编译"这种情况极其普遍**，所以面试问"你们 CI 具体跑什么、挂了怎么处理"比问"有没有 CI"更能看出水平。

### 7.8 这段经历在面试里怎么讲

> "工具是从'求职材料要压到 200KB 且不能糊字'这个具体问题出发的。核心是不做体积估算，而是对每个候选参数真编码一次、量真实字节——因为 JPEG 体积估算误差有 20%~30%。搜索上是二维网格：分辨率优先模式先按最低质量剪枝淘汰尺寸，再对质量二分，单张图 17 次左右的编码就能定下来。
>
> 工程上，我踩过一个并发确定性的坑：`-j 4` 时两个 worker 各自找空文件名，导致两个不同文件互换输出名，而这个 bug 在单进程下完全看不出来。修法是把文件名分配从并发区里拿出来，在主进程顺序分配。为此我加了一个测试，用子进程真跑 `-j 2`，再和 `-j 1` 的产物逐字节对比。
>
> CI 上用 GitHub Actions 跑 3 系统 × 2 Python 版本的矩阵，还验证了从零 `pip install` 能装上，确保别人克隆下来能用。覆盖率用 pytest-cov，徽章是自己写的 100 行脚本生成的，不依赖第三方服务。"

每一句都能在仓库里点开对应文件验证——这就是这段经历的含金量。

## 8. 动手练习清单

由易到难，每个都能独立完成：

1. **改默认预算**：把 `FitConfig.budget` 默认值改成 500KB，跑一遍测试，看看哪些测试会红（提示：依赖 200KB 的断言）。
2. **加 `--skip-existing`**：产物已存在且达标就跳过，不生成 `(1)`。改 `plan_targets` + `BatchReport` 加一个 `skipped` 计数。
3. **加 `--max-pixels`**：有些系统限制"长边不超过 2000px"。参数传给 `FitConfig.max_dim` 即可，但要处理"和预算冲突时谁优先"。
4. **GUI 双击预览**：在结果表格上绑定 `<Double-1>`，用 `os.startfile` 打开压缩后的图。注意处理"失败的行没有 target"。
5. **覆盖率门槛**：`python tools/coverage_badge.py --fail-under 80`，让 CI 在覆盖率跌破 80% 时变红。
6. **`--mode auto`**：用"接近白色像素占比 + 边缘密度"判断是文档还是照片，自动选模式。先用三张测试图验证判据，再接入。
7. **打包 exe**：PyInstaller 单文件，注意 `tkinter` 要显式包含，产物约 20MB。做完要有 CI 构建 Windows 版并挂到 Release 的步骤。

## 9. 术语速查

| 术语 | 一句话解释 |
| --- | --- |
| **CI** | 持续集成：代码一变就自动构建+测试 |
| **CD** | 持续交付（可一键发版）/ 持续部署（自动上线），两种含义要分清 |
| **workflow** | 一个 YAML 文件定义的流水线 |
| **job / step / runner** | 一台机器上的任务 / 任务里的一个命令 / 那台机器 |
| **matrix** | 一组变量做笛卡尔积，一个定义展开成 N 个 job |
| **artifact** | job 产出的文件（测试报告、构建产物），可在页面下载 |
| **cache** | 跨次运行复用的目录（如 pip 缓存），能显著缩短耗时 |
| **runner** | 执行 job 的机器，GitHub 托管或自建 |
| **LFS** | 大文件存储，本项目没用 |
| **subsampling 4:2:0** | JPEG 色度抽样：亮度全采样、色度减半，体积降约 20% |
| **Huffman 优化（optimize=True）** | 编码结束后针对本图重算最优熵编码表，同质量下更小 |
| **渐进式 JPEG** | 分多次扫描编码，弱网下先出模糊轮廓 |
| **EXIF orientation** | 照片里的"该转 90 度"标记，不处理会躺倒 |
| **原子写** | 先写临时文件再 rename，避免留下半截文件 |
| **幂等** | 跑一次和跑多次结果一样（本项目的输出目录会被排除，避免自我吞噬） |
